## 1. Done

### Commitments on Supabase

Of the second next step in the 6 November report, the server side of commitments is done:

- **Tables:** `commitments` and `commitment_events`. Only the two people concerned (requester and owner) can read them (RLS), and nobody can write them directly.
- **Changes only through database functions:** `create_commitment` and `apply_commitment_action`. They enforce the same state machine as the client (`lifecycle.ts`), with the same error messages.
- **Client:** applies the rule at once, then the server decides. A refused change is rolled back and the user is told.
- **Tests:** the online application runs 129 tests in 36 files, the state machine's among them. I tried the SQL functions on an embedded Postgres (PGlite) with 72 checks, both as an upgrade and as a fresh install. That script is not in the repository yet.

### Calendar

Month view and a day list of commitments, with a status summary. In the chat, a panel shows the day's commitments.

## 2. In progress: group conversations and commitments in the chat

I am trying these out in the offline development version (data kept in the browser) before they go to Supabase. They are not in the repository yet; they come with the Supabase version.

- **Group conversations:** with several recipients a group is created, but only with its first message. Member list, leaving the group.
- **Commitment invitation in the chat:** the suggestion shows as a card for both people and shows the same state.
- **Replying to a message:** with a reference to the source message.
- **Other:** a nickname per conversation, GIFs, files, scheduled sending, mobile view.

## 3. Not there yet

- **Rooms and membership on the server**, a single shared message stream with stable identifiers. Now every person has their own copy of each message.
- **Group commitments:** now a commitment has one requester and one owner, and only the two of them can see it.
- **Repeated processing:** there is no idempotent suggestion key yet.
- **Live updates:** the other person's change shows only after a reload.
- **Recognizer:** not connected to the application.
- **Measurement:** fixing Haiku's error types and comparing with another model family are still ahead.

## 4. Next steps (until 4 December)

1. **Rooms and membership on Supabase:** moving group conversations over, with tables, RLS and a shared message stream.
2. **Several owners in groups:** several people can take on one commitment ("Anna és Péter megcsinálja", "Anna and Péter will do it"; "Mindenki küldje el péntekig", "Everyone send it by Friday"), and each of them accepts it themselves. A commitment made in a group is visible to every member of the group.
3. **Commitment cards on the server:** one database function creates the suggestion and the card together, with live updates.
4. **Connecting the recognizer:** Haiku with the prefilter, running on the server. Its suggestions go into the same workflow as manual ones, and only the person concerned can confirm them. Idempotent key: source message + item number.
5. **Measurement:** fixing Haiku's error types on the development side only, measuring again on the held-out side, and comparing with another model family.

## 5. Question

The recognizer sends the group's messages to an external model API (Anthropic). In the prototype I use it only with test accounts and made-up conversations. With real users (Thesis II), is the consent of every group member enough, or should I switch to a local model (for example Qwen3-8B)?
